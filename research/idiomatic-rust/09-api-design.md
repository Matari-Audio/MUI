# Idiomatic Rust API design: constructors, visibility, traits, and evolution

The `mre/idiomatic-rust` repository is a peer-reviewed collection of concise, idiomatic Rust resources and points to the [Rust API Guidelines](https://github.com/mre/idiomatic-rust#projects). They are recommendations based on standard-library and ecosystem experience; following them makes an API easier to guess and interoperate with. The linked article [Elegant Library APIs in Rust](https://deterministic.space/elegant-apis-in-rust.html) gives the useful test: client code should be readable, names guessable, examples executable, valid inputs broad where conversions are obvious, and types should prevent logic errors without needless ceremony.

## Constructors and names are part of the contract

Use `new` for a general constructor and `with_*` for an alternative constructor that adds detail. Use `from_*` when the operation is a conversion constructor, but prefer the standard conversion traits when the relationship is a genuine conversion. Rust's naming table distinguishes `as_*` (cheap borrowed view), `to_*` (work or allocation while retaining the source), and `into_*` (consumes `self` and returns an owned value). A getter normally has the field's name (`config.timeout()`), not `get_timeout`; `get_*` is reserved for a single obvious lookup such as `Cell::get`. These names communicate ownership and cost at the call site, so a method called `as_bytes` that allocates, or `into_path` that merely borrows, is a correctness and usability bug, not just a style disagreement. See [C-CONV and C-GETTER](https://rust-lang.github.io/api-guidelines/naming.html).

For a zero-argument construction, implement `Default` when a meaningful default exists. An empty `new()` is still useful for collection-like types such as `Vec`, where users expect the familiar spelling. Do not make every constructor public: keep an invariant-preserving constructor public and fields private if callers must not create invalid values. Public fields are appropriate for deliberately passive records; otherwise accessors and validating setters preserve room to change representation. A bad API exposes `pub struct Port { pub value: u16 }` and later discovers it cannot enforce that `0` is forbidden. A better API uses `pub struct Port(u16); pub fn new(value: u16) -> Result<Self, PortError>`, with `get`/`get_mut`-style access only if the invariant allows it. The [future-proofing guidelines](https://rust-lang.github.io/api-guidelines/future-proofing.html) explain that public fields pin representation and permit arbitrary mutation.

```rust
// Bad: call sites cannot explain either flag.
fn widget(small: bool, round: bool) -> Widget { /* ... */ }

// Good: the constructor states the domain vocabulary.
enum Size { Small, Large }
enum Shape { Round, Square }
fn widget(size: Size, shape: Shape) -> Widget { /* ... */ }
```

Put an operation on the type when there is a clear receiver: `impl Request { pub fn send(&self) -> Result<Response, Error> }` is more discoverable and gets Rust's autoborrowing. Return a tuple or result struct for multiple outputs rather than an out-parameter, except when mutating caller-owned reusable storage is the point (for example `read(&mut [u8])`).

## Make invalid states difficult to express

Do not use positional `bool`, integer, or `Option` arguments when they have domain meanings. `Widget::new(true, false)` hides which flag is which; `Widget::new(Size::Small, Shape::Round)` documents intent and leaves room for a future `ExtraLarge`. Use a newtype when two values share a representation but not a meaning (`Miles(f64)` versus `Kilometers(f64)`), because the compiler then rejects accidental mixing. Use an enum for one-of-N choices and `bitflags` for independently combinable flags. If the input is genuinely untrusted text, parse at the boundary into the deliberate type with `FromStr` and return a meaningful parse error; accepting arbitrary strings throughout the API merely moves validation and typo handling to every caller. See [C-NEWTYPE, C-CUSTOM-TYPE, and C-BITFLAG](https://rust-lang.github.io/api-guidelines/type-safety.html) and the article's [stringly-typed discussion](https://deterministic.space/elegant-apis-in-rust.html#dont-stringly-type-your-api).

Implement applicable common traits eagerly (`Debug`, `Display`, `Clone`, `Eq`, `Hash`, `Default`, ordering traits), because orphan rules mean downstream users often cannot add an impl for a type and trait defined in other crates. Implement `From`/`TryFrom`/`AsRef`/`AsMut` where their semantics fit; do not hand-implement `Into` or `TryInto`, since blanket implementations follow from `From` and `TryFrom`. Keep generic bounds on impls and functions as narrow as the operation requires. In particular, put derived traits in `#[derive(...)]`, not as bounds on the struct declaration: `struct Good<T>(T);` with `#[derive(Clone)]` remains usable for any `T` until cloning is requested, while `struct Bad<T: Clone>(T);` unnecessarily restricts every use and makes future changes harder. See [interoperability](https://rust-lang.github.io/api-guidelines/interoperability.html) and [C-STRUCT-BOUNDS](https://rust-lang.github.io/api-guidelines/future-proofing.html).

Generics are useful when they state a real minimum assumption (`fn sum<I: IntoIterator<Item = i64>>(xs: I)`), but complex bounds hurt documentation, compile times, and error messages; use a concrete domain type when it is the actual contract.

## Builders, only when construction is actually complex

Use a builder when a value has many inputs, optional or compound configuration, multiple modes, or construction with side effects. The builder constructor should receive only required data; fluent setters should return `self` (consuming builder) or `&mut self` (non-consuming builder), and a terminal method should validate and construct the value. `Command::new(program).arg("--verbose").spawn()` is a good non-consuming pattern: it works as a one-liner and can also be configured conditionally through a mutable variable. A consuming builder is appropriate when the terminal operation must take ownership of resources, such as a writer or task closure; its setters should also consume and return `Self`, accepting reassignment in longer branches. Do not introduce a builder for two required fields with no optional behavior: it adds a state and an error path without buying readability. The [builder guideline](https://rust-lang.github.io/api-guidelines/type-safety.html#c-builder) spells out this choice and its tradeoff.

## Design for SemVer before publishing

Every public item, field, trait implementation, bound, and concrete return type is a promise. Cargo's [SemVer compatibility guide](https://doc.rust-lang.org/cargo/reference/semver.html) treats changing function arity, removing items, tightening bounds, adding a non-defaulted trait item, or adding an enum variant without `#[non_exhaustive]` as breaking changes. Therefore, prefer private fields, constructor methods, and a stable domain-level return type over exposing implementation details. Return `impl Iterator` when callers only need the iterator contract; an opaque return can still expose useful bounds such as `Clone` or `Debug` when the underlying type supports them. Use a public newtype when a stable named type or custom trait surface is itself part of the API, not merely to make those standard traits available.

Apply `#[non_exhaustive]` at the type or variant's introduction when future fields or variants are plausible. The [Rust Reference](https://doc.rust-lang.org/reference/attributes/type_system.html#the-non_exhaustive-attribute) says downstream code then cannot construct non-exhaustive structs/variants directly and must include wildcard matching, allowing additions later. Adding the attribute after users have relied on exhaustive construction can itself be breaking, so it is not a retrofit button. A public trait that downstream crates are expected to implement must remain extensible-compatible: adding a required method is breaking. If a trait is intentionally crate-controlled, document and seal it with a private supertrait; adding methods is then generally compatible because downstream cannot implement the trait, but method-resolution ambiguity can still make an addition disruptive, and removing/changing existing public methods remains breaking. Finally, avoid leaking unstable or volatile dependencies through public signatures; the API Guidelines require public dependencies of a stable crate to be stable.

The practical review question is: can a caller discover the operation, supply a valid value without guessing, handle failures with useful types, and keep compiling when internals evolve? If yes, the API is likely idiomatic. If the code relies on positional booleans, public mutable fields, arbitrary strings, unexplained generic bounds, or a builder for trivial construction, simplify toward the smallest typed contract that preserves the domain invariant.
