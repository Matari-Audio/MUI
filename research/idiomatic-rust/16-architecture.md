# Idiomatic Rust research: architecture, abstraction, and project shape

Scope: architecture and design choices surfaced by [mre/idiomatic-rust](https://github.com/mre/idiomatic-rust), checked against the linked articles and current Rust documentation on 2026-09-13. “Idiomatic” here means using the concise, conventional way Rust programmers solve a problem, rather than importing habits from another language ([repository README](https://github.com/mre/idiomatic-rust#readme)).

## The architectural rule: earn each boundary

The collection’s strongest architectural advice is to control accidental complexity. The 2025 [Be Simple](https://corrode.dev/blog/simple/) article contrasts a generic `UniversalParser<T>` plus `Box<dyn DataFormat>` with a direct CSV parser. The generic version adds layers even though the system only needs CSV:

```rust
// Good when CSV is the requirement today.
fn parse_customers(input: &str) -> Result<Vec<Customer>, csv::Error> {
    csv::Reader::from_reader(input.as_bytes()).deserialize().collect()
}
```

A good abstraction removes a repeated decision, preserves an invariant, or isolates a dependency that actually changes. A bad abstraction predicts an unproven future or adds constraints without value. A practical test is whether adding the next feature has one obvious place, needs no conversion ceremony, and remains easy to test and explain.

This does not mean “fewest types at any cost.” The same article explicitly says simplicity is not sloppiness: compile-time invariants and “illegal states unrepresentable” are justified complexity. Rust’s API Guidelines recommend newtypes for static distinctions and deliberate enums/structs instead of ambiguous booleans. Thus a good `struct UserId(u64)` or `enum Enrollment { Enrolled, Waitlisted }` prevents mix-ups; a bad design exposes raw `u64` everywhere and checks meaning only in comments. Validate at the boundary, preferably by converting into an invariant-carrying type. The API Guidelines explain that static validation catches bugs at compile time and usually moves little cost to the conversion boundary ([type safety](https://rust-lang.github.io/api-guidelines/type-safety.html), [dependability](https://rust-lang.github.io/api-guidelines/dependability.html)).

## Modules, libraries, and binaries

Rust’s module system gives a useful default architecture: crate roots (`src/lib.rs` or `src/main.rs`) declare modules; items are private by default; `pub` is an explicit API decision. The [Rust Book’s module guide](https://doc.rust-lang.org/book/ch07-02-defining-modules-to-control-scope-and-privacy.html) says modules group related code, make navigation easier, and hide implementation details. A good module exposes a small, meaningful surface and keeps fields/helpers private. A bad module marks everything `pub` “for convenience,” causing callers to depend on representation and making refactoring a breaking change. For a library, private fields plus constructors/newtypes preserve future room; for an application, crate-private (`pub(crate)`) boundaries can keep subsystems honest without pretending to publish a stable external API.

Cargo’s conventional split is equally concrete. A package may have one library (`src/lib.rs`), a default binary (`src/main.rs`), and additional binaries under `src/bin`; binaries can use the library’s public API ([Cargo targets](https://doc.rust-lang.org/cargo/reference/cargo-targets.html), [Rust Book packages and crates](https://doc.rust-lang.org/book/ch07-01-packages-and-crates.html)). A strong production shape is a reusable library containing domain/application logic and a thin `main.rs` that parses arguments, wires adapters, reports errors, and exits. This keeps CLI concerns out of the domain. A tiny one-off utility does not need a library split: start with one binary and move stable code into `lib.rs` later. The [prototyping article](https://corrode.dev/blog/prototyping/) recommends starting flat, even with inline `mod` blocks, then moving modules to files once the shape is understood.

## Generics, traits, and trait objects

Choose abstraction direction from the use site. If one function needs a capability, define the narrow trait it needs and make the function generic (`fn load<R: Repository>(repo: R)`) or use `impl Repository`. This gives static dispatch and easy compile-time substitution for tests. The API Guidelines document the tradeoff: monomorphization can increase code size and heavy bounds hurt readability ([flexibility](https://rust-lang.github.io/api-guidelines/flexibility.html)). The linked [Rust abstractions essay](https://orodu.net/2023/12/27/rust-abstractions.html) makes the same design point: put the abstraction in the consuming function’s signature instead of automatically building a virtual “storage object.”

Use `Box<dyn Trait>` when runtime heterogeneity or an open extension set is real: a GUI list containing different widgets, plugin objects, callbacks, or a factory that must select an implementation at runtime. The [Rust Book’s trait-object chapter](https://doc.rust-lang.org/book/ch18-02-trait-objects.html) shows exactly this case and contrasts it with a homogeneous generic collection. A bad pattern is a trait object for every internal service merely to mock one implementation; it can invite object-safety restrictions, dynamic dispatch, downcasting, and more indirection. A good pattern is a narrow object-safe port at a genuine runtime boundary, or a generic parameter where the implementation is known at compile time. The apparent contradiction—“use generics” versus “avoid generics”—is resolved by timing: keep prototype/application internals concrete until repeated variation exists; use generic public APIs when callers demonstrably benefit.

Macros deserve the same restraint. Use a normal function for behavior or one case. Use `macro_rules!` for small, repetitive syntax and derives/procedural macros for compile-time code generation that would otherwise be unmaintainable boilerplate. Rust’s [Reference](https://doc.rust-lang.org/reference/macros.html) distinguishes declarative and procedural macros; procedural macros run during compilation and must be in a `proc-macro` crate. The [API macro guidelines](https://rust-lang.github.io/api-guidelines/macros.html) require input syntax that resembles the generated output, support for attributes/visibility, and use wherever ordinary items are allowed. A bad macro hides control flow or creates an opaque DSL for a single call; a good derive eliminates repeated, mechanically generated implementations and is documented/tested like an API.

## Hexagonal architecture: when it earns its cost

The linked [Hexagonal architecture in Rust](https://alexis-lozano.com/blog/hexagonal-architecture-in-rust-1/) series defines the domain as business rules independent of databases, frameworks, queues, and front ends. Ports are domain-facing traits or functions; adapters implement them for HTTP, CLI, memory, or a database. Its benefits are real when the domain is valuable, infrastructure is unsettled, several front ends exist, or fast isolated domain tests matter. The series begins with use cases and validates input through newtypes (`PokemonNumber`, `PokemonName`, `PokemonTypes`), then adds exchangeable repositories and interfaces.

It is over-architecture for a tiny CRUD command with one stable storage choice. Introducing `domain`, `application`, `ports`, `adapters`, factories, and mock traits before a second adapter exists can make the path harder to follow than the problem. Start with a concrete implementation and a narrow module boundary; extract a port when a second implementation, a runtime choice, or a meaningful test seam appears. Keep pure domain computation synchronous, while adapters own runtime-specific async I/O; this avoids forcing `Send`/`Sync` bounds and a runtime onto library users ([long-term maintenance](https://corrode.dev/blog/long-term-rust-maintenance/)).

## Prototype versus production

Prototype with owned `String`/`Vec`, concrete types, type inference, `dbg!`, `todo!`, assertions, and even `unwrap` when the purpose is to discover the shape. The [prototyping guide](https://corrode.dev/blog/prototyping/) says this keeps iteration fast and makes unfinished decisions visible; it also recommends `anyhow` for contextual errors in applications. Move to production by replacing recoverable external failures with `Result`, validating inputs, removing `todo!`/`dbg!`, documenting panic/error behavior, and adding focused tests and doctests. Keep an `unwrap` only when the invariant is local, proven, and documented; an `unwrap` on user input, a file, network response, or configuration is the “ignorance” horseman’s red flag.

The [Four Horsemen talk](https://archive.fosdem.org/2024/schedule/event/fosdem-2024-2434-the-four-horsemen-of-bad-rust-code/) names the recurring failures: ignorance, excessive abstraction, premature optimization, and omission of documentation/testing. Treat `clone`, a `Vec`, or a simple allocation as acceptable in cold paths until measurement identifies a bottleneck; then optimize the algorithm or data layout first. Dependencies are also architectural commitments: Cargo supports normal, target-specific, and dev dependencies, while the maintenance guidance calls each third-party crate a liability and recommends `std` where it suffices, stable/maintained crates, minimal features, security/license checks, and regular updates ([Cargo dependencies](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html)).

The decision rule is short: begin with concrete, private, testable code; let domain invariants become types; extract boundaries only when they pay for themselves; and measure before trading readability for performance.
