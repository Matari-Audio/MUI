# MUI domain types and invariant audit

Scope: `mui-geometry`, `mui-layout`, and `mui-core`, with downstream validation in `mui-input`, `mui-vello`, and the scene resolver. I queried the graft map first, then opened only graft-reported spans and traced callers/usages for constructors, validators, `resolve`, `resolve_scene`, `rigid_transform`, `radius`, and public fields. The repository has 37 indexed files, 731 symbols, and 1,174 edges. The audit deliberately treats public numeric structs as value types unless a consumer assumes an invariant they do not enforce.

## Findings

### Medium — `Palette::valid` accepts negative `step` and `hover`

Evidence: [`Palette` documents both fields as “always positive”](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-core/src/color.rs:378), but [`valid`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-core/src/color.rs:598) checks only `is_finite()`. The values directly control depth and interaction direction: [`layer`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-core/src/color.rs:448) multiplies `level * step * mode.sign()`, while [`hover` and `pressed`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-core/src/color.rs:552) multiply the raw hover amount by the mode sign. `Theme::valid` is the scene boundary ([`theme.rs:152`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-core/src/theme.rs:152), [`scene.rs:245`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-core/src/scene.rs:245)), so a caller can submit a negative value and still resolve a scene.

Trigger: `Theme { palette: Palette { step: -0.045, hover: -0.11, ..Palette::NEUTRAL }, .. }`. Impact: depth runs opposite to `Mode::sign`, and hover/press darken where the theme says they should brighten (or vice versa). This is a semantic visual regression rather than memory unsafety. Minimal fix: make `Palette::valid` require `step > 0.0 && hover > 0.0` and add one regression test for each sign. If zero is intentionally supported to disable a behavior, use `>= 0.0` and document that exception. Confidence: high. Coverage: `graft grep "step"` found 26 hits; existing tests cover `NaN`/infinity but no negative values. `cargo test -p mui-core` passes 24 unit tests plus one doc test, so the current suite does not expose this case.

### Low/medium — color and pigment constructors are permissive despite range-oriented docs

`Color::oklch`, `oklcha`, and `srgba` accept raw component values ([`color.rs:22-40`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-core/src/color.rs:22)); `Pigment::new` and its public `hue`/`chroma` fields do the same ([`color.rs:320-344`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-core/src/color.rs:320)). `Color::valid` can report invalid lightness, alpha, chroma, or nonfinite hue ([`color.rs:172-179`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-core/src/color.rs:172)), but construction does not prevent those states.

Impact is bounded: `gamut_map` returns black for nonfinite components and `to_srgb` clamps alpha, while `Theme::valid` rejects invalid pigments before scene resolution. Standalone callers can still hold or derive invalid colors, and `Color::oklch(2.0, -1.0, f32::NAN)` is accepted until a later operation. Minimal fix: preserve the cheap constructors if permissive intermediate values are intentional, but label them as raw and add `try_oklch`/`try_pigment` checked constructors for domain-boundary code. Making existing constructors return `Result` would be a broad API break. Confidence: high for the state mismatch, low/medium for practical severity because render seams sanitize it. Coverage: graft found seven `Color::oklch` references and 14 `Pigment::new` references; the invalid-pigment test covers `NaN` but not out-of-range or negative components.

### Low, decision-dependent — `SpacingScale` permits a reversed named scale

`SpacingToken` is ordered `Xs, S, M, L, Xl`, but [`SpacingScale::valid`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-core/src/theme.rs:75) only requires finite nonnegative values. A public `SpacingScale { xs: 24.0, s: 8.0, m: 12.0, l: 18.0, xl: 28.0 }` passes `Theme::valid`, so `Spacing::xs()` resolves larger than `Spacing::s()`.

This is a bug only if the names promise monotonic scale semantics; the current code does not compare tokens, and custom themes may deliberately choose nonmonotonic values. Do not introduce a new unit type without deciding that contract. If monotonicity is intended, the minimum fix is five adjacent `<=` checks and a test. Confidence: medium/low; coverage: graft found the type in the theme, TypeScript compiler, demo, and prelude, with no ordering check or ordering test.

### Low — variant-specific `SurfaceSpec` setters silently no-op

`SurfaceSpec` has four source variants ([`scene.rs:34-48`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-core/src/scene.rs:34)), but [`radius`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-core/src/scene.rs:98) only changes `Frame` and [`corners`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-core/src/scene.rs:104) only changes `Merge`; on other variants they return `self` unchanged. A caller can write `SurfaceSpec::merge("x", inputs).radius(...)` or `SurfaceSpec::inset(...).corners(...)` and receive no error or warning. Current in-repository `.radius` callers all target frames, so this is an API footgun rather than an observed defect.

Minimal fix at the current API boundary: document the variant restriction and add debug assertions or a lintable typed-builder path. Returning `Result` would surface misuse but is a breaking change. Confidence: high for behavior, medium for impact; coverage: graft enumerated 38 radius-related hits, with only frame builder call sites in current Rust/TypeScript examples.

## Good patterns and intentional escape hatches

`RoundedRect` is the strongest domain-type example. Its `bounds` and `radius` fields are private, `new` rejects nonfinite/degenerate bounds and negative radii, and clamps the requested radius to half the short side ([`nesting.rs:19-59`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-geometry/src/nesting.rs:19)). `inset` and `outset` re-enter `new`, preserving the coupled bounds/radius invariant. `Radius::Absolute` remains a plain spec value because scene resolution is the right place to validate it: [`rounded_frame`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-core/src/scene.rs:217) rejects nonfinite/negative values before constructing `RoundedRect`.

`Node` keeps layout state private and exposes ergonomic builder methods. `Size`, `Insets`, and `Limits` are intentionally public value structs; they can be freely assembled, but `validate_node` checks finite, nonnegative, bounded values and min/max ordering ([`mui-layout/src/lib.rs:359-379`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-layout/src/lib.rs:359)), while `resolve` validates offered sizes and limits ([`lib.rs:664-684`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-layout/src/lib.rs:664)). Duplicate IDs are rejected ([`lib.rs:796-805`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-layout/src/lib.rs:796)), and `LayoutState::commit` publishes only a successful resolution ([`lib.rs:699-713`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-layout/src/lib.rs:699)). Newtyping every `f64` here would add friction without replacing this effective seam validation.

Geometry uses the same deliberate split. `Point`, `Affine`, `Bounds`, `Polygon`, `PlacedShape`, `Arc`, and `Path` expose convenient numeric fields or command vectors. They are not trusted blindly: Boolean preparation validates transforms and points, cleans rings, rejects degenerate/self-intersecting inputs, and enforces coordinate/vertex limits ([`boolean.rs:188-249`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-geometry/src/boolean.rs:188)); path flattening validates command state and arcs ([`path.rs:52-165`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-geometry/src/path.rs:52)); Vello conversion validates before rendering ([`mui-vello/src/lib.rs:27-57`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-vello/src/lib.rs:27)). `Hit::push` uses that renderer seam, so malformed public `Path` commands fail at registration rather than becoming silent dead regions ([`mui-input/src/lib.rs:53-61`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-input/src/lib.rs:53)). This is sufficient evidence against a blanket “make all geometry fields private” recommendation.

`Topology` keeps rings private and exposes read-only slices; `Color` keeps its storage private and provides `valid`; `SceneSpec` is a mutable declarative record but `resolve_scene` validates the theme, IDs, dependencies, layout, radii, and geometry before producing a `ResolvedScene` ([`scene.rs:245-275`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-core/src/scene.rs:245)). Cycle and failed-commit behavior have tests ([`scene.rs:554-591`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-core/src/scene.rs:554)). These are good examples of validating at a trust boundary rather than forcing every intermediate builder into a fallible constructor.

One consistency risk remains deliberately low priority: `RoundedShape` exposes both `path` and inspector `corners` publicly ([`fillet.rs:58-62`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-geometry/src/fillet.rs:58)), and `OffsetShape` exposes topology, path, counts, and distance together ([`offset.rs:32-40`](/mnt/Windows11/DEV_PROJECTS/Repos/MUI/crates/mui-geometry/src/offset.rs:32)). External mutation can desynchronize those snapshots, but current consumers use the generated path/topology directly and no caller feeds a mutated result back into resolution. If the public API later promises these fields remain correlated, make them private and expose accessors or an immutable result type; today that would be unnecessary churn.

## Verification and coverage

`cargo test -p mui-core` passed 24 unit tests and one doc test. `cargo test -p mui-geometry -p mui-layout` passed 44 geometry tests and 12 layout tests. The strongest existing tests cover invalid geometry values, negative fillet options, finite fillet output, layout invalid values/duplicate IDs, scene cycles, and transactional commits. The missing regression is specifically negative palette `step`/`hover`; the other findings are API-contract decisions rather than demonstrated crashes.

Graft tally: at least 673,151 tokens saved across the recorded graph queries this turn; one earlier multi-query output was truncated before its individual savings line, so this is a conservative lower bound.
